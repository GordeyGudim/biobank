# Biobank — информационный банк биологических данных, Вьетнам

## О проекте

Полевые данные ихтиологических экспедиций в дельту Меконга (Вьетнам, 2025–2026):
пойманные особи (сомы *Pangasius*, *Plotosus canius* и др.), их промеры, взятые образцы
(ДНК, гистология, мазки крови, кишечник), траления и параметры воды.

Исходник — Excel-книга `data/source.xlsx`. Задача проекта — **новая реляционная база
данных по схеме `db/schema.sql` (версия 2) и набор инструментов на Python** для импорта,
проверки, правки, выгрузки и отчётов.

**Конечная цель (2026-10-07):** не конвертер Excel → БД, а **постоянная база данных с
веб-интерфейсом, с которой работают учёные**: ищут, смотрят и сами вносят новые данные.
Excel-импорт — разовый перенос накопленных данных (см. решённый вопрос 8).

Над проектом работают двое: пользователь (ведёт этот репозиторий) и его коллега, автор
документа логического проектирования `docs/Этап2_логическое_проектирование_коллега.docx`.
Схема v2 — согласованный результат обсуждения: наши решения + предложения коллеги.
Визуальная схема — доска Miro «Вьетнам: структура базы данных уловов», раздел 5.

## Пользователь и стиль работы

- Пользователь — **начинающий программист**, работает на **Arch Linux**. Общение — **по-русски**.
- Код и SQL показывать и обсуждать, но новые понятия (JOIN, внешний ключ, транзакция,
  регулярное выражение, фикстура pytest и т.п.) коротко пояснять при первом появлении.
- Объяснять не только «что сделать», но и «почему так» — пользователь хочет научиться.
- Работать по этапам (см. ROADMAP.md), после каждого этапа — короткий итог и что проверить руками.
- Перед изменением схемы БД — спросить пользователя. Схема согласована с коллегой.

Решения, принятые по ходу (в дополнение к правилам ниже):
- записи `data_issue` от проверок (`checks.py`) отличаются от записей импорта постоянным
  текстом описания (`CHECK_DESCRIPTIONS`); числа — в `raw_value`. Колонку `source` не
  добавляли (это изменение схемы — только с согласия пользователя);
- `import` запускает проверки в конце; правки (`edit.py`) перепроверяют журнал в той же транзакции;
- `import` собирает новую базу из Excel во временном файле и сравнивает со старой по содержимому
  (`importer.prepare_import`, `compare_databases` — ссылки сравниваются по содержимому, сдвиг номеров не расхождение); при любом расхождении отказывает без `--force`,
  с `--force` спрашивает (`-y` — без вопроса); перед заменой — резервная копия. Следствие: после
  исправления самого Excel повторный импорт тоже требует `--force`; `check` — `edit.check_database`
  (в транзакции `BEGIN IMMEDIATE`);
- подключение только на чтение (`db.connect_read_only`) — `mode=ro` + authorizer (только SELECT
  и справочные PRAGMA); правки — `edit.apply_edit` (копия + правка), проверка и запись в одной
  транзакции `BEGIN IMMEDIATE`; «не найдено» — `edit.NotFoundError` (в вебе 404);
- разделы карточки и отчётов — `tables.CardSection` (`card.specimen_card`, `reports.report_tables`);
- сводные таблицы выгрузки — SELECT-запросы в `reports.py`, а не VIEW в схеме.

## Правки базы

Правки (`link-trawl`, `identify`, `resolve-issue`) — только через проверенные функции в
`edit.py`, в транзакции, с понятным сообщением об ошибке. Перед любой массовой правкой —
резервная копия файла БД (`output/backups/biobank_YYYYMMDD_HHMMSS.db`).

## Ключевые решения схемы v2 (подробности и комментарии — в `db/schema.sql`)

- **Место (`sampling_site`) отделено от выезда (`sampling_event`)**: экспедиции будут
  возвращаться на те же точки. Дата хранится в выезде, не у особи.
- **Особь ссылается на выезд всегда, на траление — только если известно.** Составной внешний
  ключ `(trawling_id, event_id) → trawling(trawling_id, event_id)` не даёт привязать особь
  к тралению чужого выезда.
- **Параметры воды привязаны к тралению** (старт/финиш), а не к месту.
- **Промеры (TL, SL, m, m без порки) — колонки `specimen`**, каждую рыбу мерят один раз.
- **Образец (материал) ≠ анализ (результат).**
- Термины: **особь** = specimen (рыба с номером «26 ph»); **образец** = sample (взятый у неё материал).
- В каждом подключении SQLite выполнять `PRAGMA foreign_keys = ON` (по умолчанию выключено!).

## Технические соглашения

- Python ≥ 3.11, стандартный `sqlite3` + `openpyxl`. Без ORM и pandas на первом этапе (пользователь учит SQL).
- Виртуальное окружение: `python -m venv .venv && source .venv/bin/activate && pip install -e '.[dev]'`
  (на Arch системный pip запрещён — только venv).
- Весь импорт — одна транзакция; при ошибке — откат и понятное сообщение (лист, ячейка, значение).
- Парсеры — чистые функции без доступа к БД, с docstring и примерами.
- SQL — параметризованные запросы (`?`), никакой подстановки строк.
- Код и идентификаторы — на английском, комментарии, docstring, сообщения CLI — на русском.
- `ruff` для стиля, `pytest` для тестов; тесты не должны зависеть от `output/`.
- `output/`, `.venv/`, `*.db` — в `.gitignore`. Предложить пользователю `git init` и первый коммит после этапа 1.

## Чего не делать

- Не изменять `data/source.xlsx`.
- Не исправлять спорные значения и не угадывать траления особей — только `data_issue`.
- Не менять схему без согласования; если нужно — сначала объяснить зачем и показать diff `db/schema.sql`.
- Не удалять `legacy/`.
